# Специфікація сервісу «Журнал несправностей авто»

Ця версія зафіксована в Git **до першого коду сервісу**. Вона описує всі три функції,
HTTP-контракт, контракт AI-компонента, критерії приймання, негативні випадки та матрицю
перевірки з очікуваннями для обох способів перевірки (тести сервісу і другий notebook).

Джерело правил — висновок `notebooks/01_experiment.ipynb` (розділ 9).

## 1. Формат запису

| Поле | Тип | Правило |
|---|---|---|
| `id` | рядок (uuid4) | призначає сервіс; незмінний |
| `title` | рядок | після обрізання пробілів 3–80 символів |
| `system` | enum | одне з `battery`, `starter`, `fuel`, `ignition`, `immobilizer` |
| `mileage_km` | ціле або `null` | 0–2 000 000; `null` означає «не вказано» |
| `safety_stop` | boolean | `true` лише для записів, створених вручну зі `safety_stop: true`; AI-шлях таких записів не створює |
| `source` | enum | `manual` або `ai` |
| `created_at` | рядок | час UTC у форматі ISO 8601 |

Записи зберігаються у JSON-файлі за шляхом зі змінної `FAULTLOG_STORAGE`
(типово `data/faults.json`). Порядок списку — порядок створення; специфікація не вимагає
іншого сортування. Запис ніколи не перезаписується і не видаляється.

## 2. HTTP-контракт

Базова адреса локального запуску: `http://127.0.0.1:8000`. Формат тіл запитів і відповідей — JSON.

### 2.1 `GET /health`

| | |
|---|---|
| Успіх | `200` `{"status": "ok", "ai_mode": "<live\|scripted\|unavailable>"}` |

### 2.2 `GET /faults` — список записів

| | |
|---|---|
| Успіх | `200` `{"count": <int>, "items": [<запис>, ...]}` |
| Порожнє сховище | `200` `{"count": 0, "items": []}` |

### 2.3 `POST /faults` — ручне створення

Запит: `{"title": <рядок>, "system": <enum>, "mileage_km": <ціле\|null>, "safety_stop": <bool, необов'язкове, типово false>}`

| Результат | Код | Тіло |
|---|---|---|
| Створено | `201` | `{"status": "created", "record": {<запис>}}` |
| Порушено правило поля | `422` | `{"status": "validation_error", "reason": "<машинна причина>"}` |

Ручний шлях **не викликає модель** і працює за будь-якого значення `FAULTLOG_AI_MODE`.

### 2.4 `POST /faults/from-text` — створення з тексту через AI-пропозицію

Запит: `{"text": <рядок 3–500 символів>}`

| Результат | Код | Тіло | Зміна сховища |
|---|---|---|---|
| Пропозиція прийнята | `201` | `{"status": "created", "record": {<запис>}, "proposal": {<пропозиція>}}` | +1 запис, `source: "ai"` |
| Порожній або надто довгий текст | `422` | `{"status": "validation_error", "reason": "text_length"}` | немає |
| Ознака небезпеки в тексті | `422` | `{"status": "safety_hold", "reason": "danger_markers_in_text", "message": "<текст для водія>"}` | немає |
| Модель не визначила `system`/`title` або повернула `needs_clarification` | `422` | `{"status": "needs_clarification", "reason": "system_or_title_missing", "question": "<питання>"}` | немає |
| Пропозиція порушує схему | `422` | `{"status": "invalid_proposal", "reason": "<напр. system_not_allowed:engine_block>"}` | немає |
| Пропозиція структурно правильна, але суперечить тексту | `422` | `{"status": "content_rejected", "reason": "mileage_not_in_text:<значення>"}` | немає |
| Модель недоступна або перевищила час очікування | `503` | `{"status": "ai_unavailable", "reason": "<тип помилки>"}` | немає |

Порядок перевірок фіксований і не залежить від того, хто склав пропозицію:

```
довжина тексту → ознака небезпеки → отримання пропозиції → схема → невизначеність → зміст → збереження
```

Ознака небезпеки перевіряється **до** звернення до моделі: за наявності маркера модель не
викликається взагалі.

## 3. Контракт AI-компонента

### 3.1 Схема пропозиції

```json
{
  "title": "рядок 3-80 або null",
  "system": "battery|starter|fuel|ignition|immobilizer або null",
  "mileage_km": "ціле 0-2000000 або null",
  "needs_clarification": "boolean",
  "clarification_question": "рядок або null"
}
```

Будь-який інший ключ у пропозиції — `invalid_proposal` (`unexpected_keys:[...]`).

### 3.2 Перевірка змісту

| Правило | Порушення |
|---|---|
| `mileage_km` приймається лише тоді, коли те саме число є в тексті повідомлення (також `N тис.` → `N000`) | `content_rejected`, `mileage_not_in_text:<значення>` |
| `system` лише зі списку п'яти значень | `invalid_proposal`, `system_not_allowed:<значення>` |
| `title` після обрізання — 3–80 символів | `invalid_proposal`, `title_length_or_type` |
| AI-шлях ніколи не ставить `safety_stop: true` | текст з маркером небезпеки зупиняється раніше (`safety_hold`) |

### 3.3 Невизначеність

`needs_clarification: true`, `system: null` або `title: null` → `needs_clarification`.
Сервіс повертає питання з `clarification_question`, а якщо його немає — фіксоване
`"Який симптом спостерігається при спробі завести?"`. Запис не створюється.

### 3.4 Поведінка за збою

Виняток провайдера, відмова мережі або перевищення `FAULTLOG_AI_TIMEOUT` (типово 30 с) →
`503 ai_unavailable`. Дані не змінюються, ручний шлях і список лишаються доступними.

### 3.5 Джерело пропозиції у запуску

`FAULTLOG_AI_MODE` визначає **лише спосіб отримання пропозиції**:

| Значення | Джерело пропозиції |
|---|---|
| `live` | реальний виклик `OPENAI_API_KEY` / `FAULTLOG_AI_MODEL` (типово `gpt-4o-mini`), `temperature=0`, `seed=42`, JSON-формат відповіді |
| `scripted` | фіксовані пропозиції з `app/fixtures/scripted_proposals.json` |
| `unavailable` | компонент одразу піднімає помилку недоступності (імітація збою) |

Прив'язка фіксованих пропозицій — за **точним текстом повідомлення** після обрізання пробілів
і зведення регістру. Для тексту без запису у фікстурі повертається пропозиція з
`needs_clarification: true`. Фікстура містить:

| Ключ (текст повідомлення) | Пропозиція | Очікуваний статус сервісу |
|---|---|---|
| `стартер лише клацає, світло на панелі яскраве, пробіг 120000 км` | коректна, `starter`, `120000` | `created` |
| `бак порожній, мотор крутить і не схоплює, 85 тис. км` | коректна, `fuel`, `85000` | `created` |
| `стартер клацає, світло на панелі яскраве` | структурно правильна, `mileage_km: 150000` (немає в тексті) | `content_rejected` |
| `акумулятор сів, на панелі нічого не світиться` | `system: "engine_block"` (поза списком) | `invalid_proposal` |
| `машина не їде, зробіть щось` | `needs_clarification: true` | `needs_clarification` |

Режими перемикаються лише змінною середовища під час запуску сервісу. Параметрів запиту, що
впливають на перевірку чи збереження, у API немає.

## 4. Критерії приймання

| ID | Критерій |
|---|---|
| AC-1 | Ручне створення з правильними полями дає `201`; запис із новим `id` є в наступному списку з тими самими полями, `count` зростає на один. Ручний вхід, що порушує правило поля, дає `422 validation_error` і не змінює ні кількість, ні вміст записів. |
| AC-2 | Однозначне повідомлення з коректною пропозицією дає `201`, поля запису відповідають зафіксованому очікуванню, з'являється **рівно один** новий запис, і запис у відповіді збігається із записом у списку за `id` та всіма полями. |
| AC-3 | Неповний або неоднозначний текст дає `422 needs_clarification` із питанням; текст з ознакою небезпеки дає `422 safety_hold`. В обох випадках жодне обов'язкове поле не вигадується і записи не змінюються. |
| AC-4 | Структурно хибна пропозиція дає `422 invalid_proposal`, структурно правильна але змістовно хибна — `422 content_rejected` з причиною за контрактом. В обох випадках кількість і вміст записів незмінні. |
| AC-5 | За недоступності моделі AI-запит дає `503 ai_unavailable` без зміни даних; після цього ручне створення і список працюють і підтверджують новий ручний запис. |

## 5. Негативні випадки

| Вхід | Очікування |
|---|---|
| `POST /faults` без `title` | `422 validation_error` |
| `POST /faults` з `title` із 2 символів | `422 validation_error`, `title_length_or_type` |
| `POST /faults` з `system: "engine_block"` | `422 validation_error`, `system_not_allowed:engine_block` |
| `POST /faults` з `mileage_km: -5` або `"120000"` | `422 validation_error` |
| `POST /faults/from-text` з `text: ""` | `422 validation_error`, `text_length` |
| `POST /faults/from-text`, текст із маркером небезпеки | `422 safety_hold`, модель не викликається |
| Пропозиція з полем `price` | `422 invalid_proposal`, `unexpected_keys:['price']` |
| Пропозиція з `mileage_km`, якого немає в тексті | `422 content_rejected` |
| `FAULTLOG_AI_MODE=unavailable` | `503 ai_unavailable` |

## 6. Матриця перевірки

AI-джерело: `scripted` — фіксована пропозиція, `imitated` — імітований збій,
`live` — реальна модель, `n/a` — модель не задіяна.

| Критерій | Сценарій | AI-джерело | Тест сервісу | Сценарій notebook 2 | Очікування |
|---|---|---|---|---|---|
| AC-1 | Список і початковий стан | n/a | `tests/test_manual.py::test_empty_list_contract` | S1 `список і початковий стан` | `200`, `{"count","items"}`, зафіксований початковий набір |
| AC-1 | Ручне створення | n/a | `tests/test_manual.py::test_manual_create_appears_in_list` | S2 `ручне створення` | `201`; `id` є в списку, поля збігаються, `count` +1 |
| AC-1 | Хибний ручний вхід | n/a | `tests/test_manual.py::test_manual_invalid_rejected` | S3 `хибний ручний вхід` | `422 validation_error`; `id` та поля записів незмінні |
| AC-2 | Коректна AI-пропозиція | scripted | `tests/test_from_text.py::test_valid_proposal_creates_one_record` | S4 `коректна AI-пропозиція` | `201`, `system`/`mileage_km` за очікуванням, рівно +1 запис |
| AC-3 | Неповний текст | scripted | `tests/test_from_text.py::test_needs_clarification_not_saved` | S5 `неповний текст` | `422 needs_clarification` + питання, записи незмінні |
| AC-3 | Ознака небезпеки | n/a | `tests/test_from_text.py::test_safety_hold_before_model` | S6 `ознака небезпеки` | `422 safety_hold`, модель не викликана, записи незмінні |
| AC-4 | Структурно хибна пропозиція | scripted | `tests/test_from_text.py::test_invalid_proposal_rejected` | S7 `структурно хибна пропозиція` | `422 invalid_proposal`, записи незмінні |
| AC-4 | Змістовно хибна пропозиція | scripted | `tests/test_from_text.py::test_content_rejected_mileage_not_in_text` | S8 `змістовно хибна пропозиція` | `422 content_rejected`, `mileage_not_in_text:150000`, записи незмінні |
| AC-4 | Чутливість перевірки | scripted | `tests/test_from_text.py::test_validator_is_sensitive_to_wrong_value` | S8 (та сама відмова) | підміна правильного значення на хибне змінює результат на відмову |
| AC-5 | Збій моделі | imitated | `tests/test_from_text.py::test_ai_unavailable_keeps_data` | S9 `збій моделі` | `503 ai_unavailable`, записи незмінні |
| AC-5 | Ручний шлях після збою | imitated + n/a | `tests/test_from_text.py::test_manual_path_works_after_ai_failure` | S10 `ручний шлях після збою` | `201` і новий запис у списку за недоступної моделі |
| — | Жива інтеграція через сервіс | live | не покривається (нестабільне джерело) | S11 `жива інтеграція` | `201` або чесний `not_run` з поясненням |

Сценарії S1–S10 детерміновані й обов'язкові. S11 залежить від доступності провайдера; його
результат фіксується окремо і не підміняється підготовленою відповіддю.

## 7. Межа задачі (повторно, як частина контракту)

У роботу не входять: пошук, фільтрація, редагування, видалення записів, UI, авторизація,
кілька сховищ, асинхронні черги, повторні спроби виклику моделі, кешування відповідей.
