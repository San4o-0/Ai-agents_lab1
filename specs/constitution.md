# Правила проєкту (constitution)

Версія цього файла керувала розробкою до першого коду сервісу.

## Межа задачі

1. Сервіс має рівно три функції: ручне створення запису, перегляд списку записів, створення
   запису з короткого тексту через AI-пропозицію з перевіркою.
2. Усі три функції доступні через локальний HTTP API. CLI, UI, авторизація, хмара, пошук,
   редагування та видалення записів **не входять** до роботи.
3. Сховище — один локальний JSON-файл. База даних і міграції не додаються.
4. Жодних реальних персональних даних, платежів, бронювань і зовнішніх дій, крім виклику
   LLM-провайдера.

## Правила перевірки

1. Специфікація всіх трьох функцій і очікування для зовнішньої перевірки фіксуються в Git
   **до** першого рядка коду сервісу.
2. Кожен критерій приймання має автоматичний тест сервісу і сценарій у другому notebook.
3. Детерміновані перевірки не залежать від реальної моделі: пропозиція AI-компонента
   підміняється фіксованою всередині сервісу.
4. Підміна стосується **лише отримання пропозиції**. Обробники, перевірка і збереження в
   тестовому запуску ті самі, що у звичайному.
5. До API не додаються параметри обходу перевірки, прямого запису або примусового успіху.
6. Код HTTP і змістовий статус перевіряються окремо: `201` сам по собі не доводить, що поля
   правильні.
7. Очікування не переписуються під відповідь моделі. Невдала відповідь показується як помилка
   моделі.
8. Другий notebook працює лише через HTTP: він не імпортує код сервісу, не використовує
   `TestClient` і не звертається до провайдера напряму.

## Правила роботи з агентом для програмування

1. Кожну фазу (`specify`, `clarify`, `plan`, `tasks`, `implement`) переглядає студент і фіксує,
   що прийнято, уточнено або відхилено.
2. План не розширює межу трьох функцій; задачі ведуть до критеріїв приймання.
3. Пропозиція агента не є підтвердженням: рішення приймає студент і перевіряє результат
   запуском тестів і зовнішньою перевіркою.
4. Секрети не потрапляють у код, notebooks, коміти чи вивід: ключ лише в Git-ignored `.env`.

## Межа AI-компонента

1. Модель **не має прямого доступу до сховища**: вона повертає пропозицію, сервіс її приймає
   або відхиляє.
2. Рішення про небезпеку (`safety_stop`) приймає детермінований код за фіксованим списком
   маркерів, а не модель.
3. Недоступність моделі має визначений результат і не змінює дані.
4. Ручний шлях не залежить від моделі й лишається доступним після її збою.
